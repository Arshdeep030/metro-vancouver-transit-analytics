# Synapse Serverless SQL Serving Layer Documentation

## 1. Executive Summary & Design Rationale

The serving layer of the Metro Vancouver Transit Analytics platform is implemented using **Azure Synapse Serverless SQL** (`syn-transit-analytics-ondemand.sql.azuresynapse.net`). It provides a lightweight, zero-copy, highly scalable relational abstraction over the curated Gold Parquet datasets in Azure Data Lake Storage (ADLS) Gen2.

```text
               ADLS Gen2 Gold
        (Snappy Parquet Datasets)
                   │
                   │ OPENROWSET (Direct Lakehouse Query)
                   ▼
       ┌────────────────────────┐
       │ Synapse Serverless SQL │
       │    Built-in Compute    │
       │ Database: TransitAnalytics
       └───────────┬────────────┘
                   │
                   │ Curated SQL Views
                   ▼
       ┌────────────────────────┐
       │   Power BI Dashboard   │
       │ DirectQuery or Import  │
       └────────────────────────┘
```

### Why Synapse Serverless SQL?
1. **Zero Idle Infrastructure Cost:** Unlike Dedicated SQL Pools (which incur continuous hourly compute charges even when idle), Serverless SQL charges only per terabyte of data processed by queries ($5 per TB). In this lakehouse architecture, data queries scan only megabytes per execution.
2. **Instant Scaling & High Concurrency:** Handles BI dashboards, ad-hoc analyst exploration, and scheduled reporting without manual cluster scaling, pause/resume scripts, or queue management.
3. **Decoupled Storage and Compute:** Storage remains purely in ADLS Gen2 object storage while compute is provisioned on demand by the SQL engine.

### Why ADLS Gen2 Remains the Physical Storage Layer
1. **Single Source of Truth:** Data is not copied or duplicated into relational database tables. Parquet files generated by Synapse Spark serve as the authoritative single copy of data.
2. **Schema Evolution & Open Standards:** Downstream consumers (Spark, SQL, Python, Databricks, Power BI) can query the underlying Snappy Parquet files directly using standard open formats.
3. **Avoids ETL Data Duplication:** Traditional enterprise warehouses copy data from lakes into relational tables, creating latency, synchronization overhead, and double storage billing. Synapse Serverless SQL queries Parquet directly in place.

## 2. Serverless Database & Architecture

* **Synapse Workspace:** `syn-transit-analytics`
* **Serverless SQL Endpoint:** `syn-transit-analytics-ondemand.sql.azuresynapse.net`
* **Database Name:** `TransitAnalytics`
* **Security & Authentication:** Synapse Workspace Managed Identity / Microsoft Entra ID (Azure AD). Zero connection strings, storage account keys, or SAS tokens stored in source code.

### External Data Access Topology

```sql
-- Database Scoped Credential using Synapse Workspace Managed Identity
CREATE DATABASE SCOPED CREDENTIAL WorkspaceIdentity
WITH IDENTITY = 'Managed Identity';

-- External Data Source pointing to ADLS Gen2 Gold container
CREATE EXTERNAL DATA SOURCE GoldDataLake
WITH (
    LOCATION = 'https://stransitanalytics.dfs.core.windows.net/gold',
    CREDENTIAL = WorkspaceIdentity
);
```

## 3. View Definitions & Mapping

All views are deployed under the `dbo` schema in database `TransitAnalytics`:

### 3.1 `dbo.vw_route_performance`
* **Underlying Path:** `abfss://gold@stransitanalytics.dfs.core.windows.net/route_performance/**`
* **Grain:** `route_id`
* **Record Count:** 175 routes
* **Purpose:** Route punctuality, arrival/departure average delays, category rates (on-time, early, delayed, severely delayed, unknown).

```sql
CREATE OR ALTER VIEW dbo.vw_route_performance AS
SELECT
    CAST([route_id] AS VARCHAR(50)) AS [route_id],
    CAST([route_short_name] AS VARCHAR(50)) AS [route_short_name],
    CAST([route_long_name] AS VARCHAR(255)) AS [route_long_name],
    CAST([observation_count] AS BIGINT) AS [observation_count],
    CAST([avg_arrival_delay_minutes] AS FLOAT) AS [avg_arrival_delay_minutes],
    CAST([avg_departure_delay_minutes] AS FLOAT) AS [avg_departure_delay_minutes],
    CAST([on_time_count] AS BIGINT) AS [on_time_count],
    CAST([on_time_rate] AS FLOAT) AS [on_time_rate],
    CAST([delayed_count] AS BIGINT) AS [delayed_count],
    CAST([delayed_rate] AS FLOAT) AS [delayed_rate],
    CAST([severely_delayed_count] AS BIGINT) AS [severely_delayed_count],
    CAST([severely_delayed_rate] AS FLOAT) AS [severely_delayed_rate],
    CAST([early_count] AS BIGINT) AS [early_count],
    CAST([early_rate] AS FLOAT) AS [early_rate],
    CAST([unknown_delay_count] AS BIGINT) AS [unknown_delay_count],
    CAST([unknown_delay_rate] AS FLOAT) AS [unknown_delay_rate],
    CAST([extreme_delay_count] AS BIGINT) AS [extreme_delay_count],
    CAST([first_observed_at] AS DATETIME2) AS [first_observed_at],
    CAST([last_observed_at] AS DATETIME2) AS [last_observed_at]
FROM OPENROWSET(
    BULK 'route_performance/**',
    DATA_SOURCE = 'GoldDataLake',
    FORMAT = 'PARQUET'
) AS [r];
```

### 3.3 `dbo.vw_delay_analysis`
* **Underlying Path:** `abfss://gold@stransitanalytics.dfs.core.windows.net/delay_analysis/service_date=*/**`
* **Grain:** `(service_date, observation_hour, day_of_week, route_id, route_short_name, direction, delay_category)`
* **Record Count:** 1,210 multidimensional slices
* **Partition Pruning:** Uses `CAST(d.filepath(1) AS DATE) AS [service_date]`, enabling Synapse Serverless SQL to prune entire directory partitions when date filters are applied by Power BI.

```sql
CREATE OR ALTER VIEW dbo.vw_delay_analysis AS
SELECT
    CAST(d.filepath(1) AS DATE) AS [service_date],
    CAST([observation_hour] AS INT) AS [observation_hour],
    CAST([day_of_week] AS VARCHAR(20)) AS [day_of_week],
    CAST([route_id] AS VARCHAR(50)) AS [route_id],
    CAST([route_short_name] AS VARCHAR(50)) AS [route_short_name],
    CAST([direction] AS VARCHAR(50)) AS [direction],
    CAST([delay_category] AS VARCHAR(50)) AS [delay_category],
    CAST([observation_count] AS BIGINT) AS [observation_count],
    CAST([avg_delay_minutes] AS FLOAT) AS [avg_delay_minutes],
    CAST([min_delay_minutes] AS FLOAT) AS [min_delay_minutes],
    CAST([max_delay_minutes] AS FLOAT) AS [max_delay_minutes],
    CAST([on_time_count] AS BIGINT) AS [on_time_count],
    CAST([delayed_count] AS BIGINT) AS [delayed_count],
    CAST([severely_delayed_count] AS BIGINT) AS [severely_delayed_count],
    CAST([early_count] AS BIGINT) AS [early_count],
    CAST([unknown_delay_count] AS BIGINT) AS [unknown_delay_count]
FROM OPENROWSET(
    BULK 'delay_analysis/service_date=*/**',

```

## 4. Power BI Consumption Pattern

Power BI connects directly to the Synapse Serverless SQL endpoint using the native **Azure Synapse Analytics (SQL DW)** connector or standard **SQL Server** connector:

| Setting | Value |
| :--- | :--- |
| **Server** | `syn-transit-analytics-ondemand.sql.azuresynapse.net` |
| **Database** | `TransitAnalytics` |
| **Authentication** | Microsoft Account (Azure Active Directory / Entra ID) |
| **Data Connectivity Mode** | **Import** (recommended for sub-second dashboard rendering) or **DirectQuery** |


## 5. Analytical Observations (During the Observed Period)

> [!NOTE]
> All findings below reflect observations collected between **02:03:00 and 02:35:00 UTC on October 4, 2026** (19:03:00 to 19:35:00 Vancouver local time).

1. **System Health:** During this 32-minute window, the network registered an overall **on-time rate of 30.59%**, with an average delay of **1.17 minutes** and median delay of **0.17 minutes**.
2. **Corridor Delay Concentration:** Routes operating across the Burrard Inlet (North Shore to Downtown Vancouver corridor) experienced the highest severe delay rates:
   * **Route 250 (Horseshoe Bay / Dundarave / Vancouver):** 64.06% severe delay rate (avg delay: 11.66 min).
   * **Route 240 (Lynn Valley / Downtown):** 62.96% severe delay rate (avg delay: 15.56 min).
3. **Stop Hotspots:** The stops with the longest delays during the period were clustered along the West Keith Rd / Marine Dr / West Georgia corridor (e.g. Stop 4500 on Keith Rd at 16.93 min avg delay; Stop 985 on West Georgia at Granville St at 16.83 min avg delay).
